# Troubleshooting

Problems are grouped by stage, with the exact message where there is one. Behaviour that v1 documents rather than changes is collected under [Known limitations](#known-limitations). For the setup see [hardware.md](hardware.md), [calibration.md](calibration.md) and [anygrasp_license.md](anygrasp_license.md).

## Where to look first

- **Preparation** (`scripts/anygrasp_poses_one_shot.sh`):
  - one log per stage in `<case>/logs/`;
  - the capture settings in `<case>/anygrasp/anygrasp_collection_summary.json`;
  - the prompt (`category`), `mask_object_id` and fusion values in `<case>/anygrasp/observation/raw_to_fused_observation_run_meta.json`;
  - the grasp decisions and filter thresholds (`configuration`) in `<case>/anygrasp_results/grasps_table_ik_report.json`;
  - the prompt, paths and observation-filter values of the last call in `<case>/one_shot_summary.json`, even when that call was a resume that skipped stages 01-03 (by default, every lift run on a prepared case is one).
- **Lift run** (`scripts/run_anygrasp_to_lift_one_shot.sh`): its own stages print to the console only (the preparation stages it runs still log to `<case>/logs/`). Keep a log with `... 2>&1 | tee <file>`; the checkpoints still read from the terminal. Such a log contains absolute paths and the camera MXIDs, and usually the robot address, so keep it out of published data ([Before sharing data](data_format.md#before-sharing-data)). The recording quality is in `<case>/phystwin/recording_summary.json`, and `global_one_shot_summary.json` is written only after a complete run.
- **Messages.** The shell scripts stop with `[ERROR] <reason>` and name the setting or file that is missing. `bash scripts/<script>.sh --help` lists every option with its default.
- **Calibration tools** print to the terminal. The hand-eye tool's `--diagnose-only`, and a run that stops with too few samples, also write `scan_records_debug.json` (bundle checks) and `pose_filter_logs_debug.json` (pose-diversity filter).

## Configuration and environments

- **`AURA_OAK_IDS is empty`, `no OAK camera ids`, `Robot IP not set`, `--execute needs the robot IP`, `--execute needs the OAK MXIDs`, `No robot IP`, `No OAK cameras`, `no anchor camera`.** Fill in `config/aura.env` (copied from `config/aura.env.example`). The scripts in `scripts/` load it themselves. Before running a Python tool directly, load it with `set -a; source config/aura.env; set +a`. The recording executor run by hand prints `--execute needs the OAK MXIDs`, the teleoperation recorder prints `No robot IP` or `No OAK cameras`, and the re-anchoring tool prints `no anchor camera` when `AURA_HANDEYE_OAK_ID` is unset and no `--anchor` is given.
- **`config/aura.env: source this file from bash, or export AURA_REPO_ROOT=<path to the repository> first`.** The file was sourced from another shell, such as zsh or sh, where it cannot find the repository by itself. Source it from bash, or export `AURA_REPO_ROOT` first.
- **A directory named `~` appears in the directory you ran a script from.** A path in `config/aura.env`, or one you exported, starts with `~/` inside quotes, and bash does not expand a `~` there. Write it as `$HOME/...` or as another absolute path.
- **An option has a different value than you passed or configured.** The scripts also read an environment variable for most options, which overrides the defaults and `config/aura.env`.
  - Most are named like their options (`ROBOT_IP`, `DATA_ROOT`, `SAFE_INDEX`, `TOP_K`, `SYNC_TOLERANCE_MS`, `OMP_NUM_THREADS`, `FORCE`, `RESUME`, ...); some are not: `AUTO_YES` (`--yes`) and `HOME_ROBOT` (`--home`) in the lift one-shot, `ROBOT_DESCRIPTION` (`--description`), `RUN_PYROKI` (`--pyroki-filter`), `USE_SOFT_LIMITS` (`--soft-limits`) and `NO_COLLISION_FALLBACK` (`--collision-fallback`; `1` enables it) in the preparation script, and `LIVE_PREVIEW` (`--preview`) in the human-baseline recorder.
  - `--rot-offset-rpy` of the lift one-shot and of the preparation script can be set only on the command line: an exported `ROT_OFFSET_RPY` is ignored. The lift one-shot's `POSE_FRAME` can be set only as an environment variable.
  - On/off variables count as on only when set to `1`; any other value, `true` and `yes` included, counts as off without a message, so `USE_SOFT_LIMITS=true` disables the soft joint limits. `OVERWRITE` must be `0` or `1`; `PREVIEW`, `RECORD_PREVIEW` and `LIVE_PREVIEW` take `True` or `False`.
- **A stale export changes every later run.** Before a session, run `env | grep -E '^(AUTO_YES|OVERWRITE|HOVER_ONLY|FINALIZE_EXISTING_RECORDING|FORCE|RESUME|REFILTER|HOME_ROBOT|SAFE_INDEX|DATA_ROOT|RECORD_[A-Z_]+|CAMERA_WARMUP_SECONDS|SYNC_TOLERANCE_MS)='` and `unset` what it prints: the run summaries record only some of these values, and some switches have no option that turns them off.
  - Lift one-shot: `AUTO_YES=1` skips every robot checkpoint, including the one before the final release-and-home step; `OVERWRITE=1` deletes the whole case, recordings included, without asking; `HOVER_ONLY=1` makes every lift hang at hover; `FINALIZE_EXISTING_RECORDING=1` releases and homes on every resume of a recorded case.
  - Preparation script: `FORCE=1`, `RESUME=1` and `REFILTER=1` apply to every run, and with `FORCE=1` every lift run on an existing case stops with `--force and --resume are mutually exclusive`.
  - Shared names: the human-baseline recorder reads the same `OVERWRITE`, `DATA_ROOT` and `CAMERA_WARMUP_SECONDS` as the lift one-shot, so an `OVERWRITE=1` exported for hand takes also makes every lift run delete its case. `RECORD_*` and `CAMERA_WARMUP_SECONDS` exported for the lift also change the preparation's static capture, and the human-baseline recorder's `SYNC_TOLERANCE_MS` also sets the preparation's static sync tolerance unless `STATIC_SYNC_TOLERANCE_MS` is set.
- **A value you changed in `config/aura.env` has no effect, or a `set ... in config/aura.env` error comes back after you set it.** A shell that has loaded the file keeps every non-empty value it loaded, also after you source the file again and in every script started from that shell. Open a new terminal, or run `unset ${!AURA_*} ANYGRASP_ENV`, then load the file again.
- **A file or folder you passed is not found partway through a preparation or lift run.** Give path options of `scripts/anygrasp_poses_one_shot.sh` and `scripts/run_anygrasp_to_lift_one_shot.sh` as absolute paths: `--aura-root`, `--state-file`, `--robot-calib`, `--robot-calib-results`, `--filter-script`, `--anygrasp-checkpoint` and `--camera-extrinsic-dir`, also when you pass preparation options to the lift one-shot after `--`. The preparation script changes directory between stages, so a relative path can fail partway through a run, before any robot motion, and a relative `--anygrasp-checkpoint` can be silently replaced ([anygrasp_license.md](anygrasp_license.md#5-checkpoint)).
- **`ModuleNotFoundError` for `fr3` or `pylibfranka`.** These exist only in the robot environment. Run robot scripts as `uv run --project environments/robot python aura/robot/<script>.py`, after `uv sync --project environments/robot`.
- **`Failed to import depthai`.** The script runs in the wrong environment. Camera-only tools run in `AuRA`; robot scripts run with `uv run` as above.
- **A calibration tool fails in `cv2.aruco`.** For example, `interpolateCornersCharuco` or `CharucoDetector` is missing. Another `pip install` replaced the `cv2` the calibration needs: follow [the opencv-contrib 4.7.0 hazard](../environments/README.md#the-opencv-contrib-470-hazard). If the check still fails after that fix, or `cv2` reports a numpy problem, a package in `~/.local/lib/python3.10/site-packages` may shadow the env: see the user-site note in [environments/README.md](../environments/README.md#notes).
- **GroundingDINO errors after a package upgrade.** `transformers` is pinned to 4.37.2 on purpose (`environments/aura.yml`).
- **`nvcc: command not found` while building.** `export CUDA_HOME=<your CUDA 12.8 toolkit>` and `export PATH="$CUDA_HOME/bin:$PATH"` ([System requirements](../environments/README.md#system-requirements)).
- **The first stage-02 or stage-04 run stalls or fails without network access.** GroundingDINO downloads `bert-base-uncased`, and the grasp filter downloads `franka_description`, the first time they run ([First-run downloads](../environments/README.md#first-run-downloads)).
- **`Failed to load custom C++ ops. Running on CPU mode Only!` in the stage-02 log.** `groundingdino._C` was built without CUDA. Rebuild the Grounded-SAM-2 editable installs with a CUDA 12.8 toolkit (post-install step 3 of `environments/aura.yml`).

## Robot connection and real-time

- **A robot script fails with a real-time scheduling error.** Run the checks in [hardware.md](hardware.md#real-time-kernel). Start robot scripts that you run by hand from a shell without an active conda env; the lift one-shot is the exception and starts with the `AuRA` env active, as the Shell item there says. A container needs real-time rights too.
- **Cannot connect, or `ping <ROBOT_IP>` gets no answer.** Bring the wired link up and check the workstation's address on the robot network. In Franka Desk, unlock the joints and activate FCI. Make sure no other program, such as a teleoperation session, holds the arm connection.
- **Reflex or collision errors during a move.** The robot touched something, or a commanded move was too demanding. The robot scripts call `automatic_error_recovery()` when they connect. If reflexes recur on free-space moves, check that no leftover segmentation or AnyGrasp process is loading the machine.
  - **Standalone executor: press the emergency stop at the first contact.** The Cartesian moves of the `fr3` wrapper, which this executor uses, are retried up to 3 more times, each with a 1.5 times longer duration, after reflex and discontinuity errors, collision reflexes included: after a contact the arm drives towards the same target again. An emergency stop is not retried.
  - The recording executor's own control loop does not retry.

## Preparation one-shot

### Re-runs

- **`Case exists: ...`.** Pass `--resume` to skip the stages whose outputs exist and run the others, or `--force` to delete the preparation outputs and capture the scene again while keeping `phystwin/` (never on a case that already has a lift recording in `phystwin/raw_recording/`). The two options exclude each other.
- **`--resume` started a new capture.** Resuming is keyed on `<data-root>/<case>`. Pass the same `--data-root` to the preparation script and the lift one-shot of a case.
- **`--refilter` had no effect.** It works only together with `--resume`.
- **Which stages `--resume` skips.** Each stage is checked against its own outputs only:
  - stage 01 is skipped if `anygrasp/calibrate.pkl`, `anygrasp/color/0/0.png` and `anygrasp/depth/0/0.npy` exist;
  - stage 02 if `anygrasp/observation/observation_frame000_filtered.npz` exists;
  - stage 03 if a `grasps.json` with grasps exists in `anygrasp_results/` or `anygrasp_results_no_collision/`;
  - stage 04 if both filter outputs exist, unless `--refilter` is given.

  A stage that runs again does not re-run the later ones: their old outputs, the grasps and the safe list included, are reused, and the lift one-shot's default `--refilter` only re-filters the old grasps. A new capture is the exception: it also redoes stage 02, because stage 01 replaces `anygrasp/`.
- **Redoing stage 02 or 03 on the same capture.** Delete `anygrasp/observation/` (stage 02 only), `anygrasp_results/` and `anygrasp_results_no_collision/`, then pass `--resume`. `--force` redoes every stage from a new capture.

### Stage 01: static capture

- **`No recorded frames for oak_<MXID>`.** A camera delivered no frames, or q or Esc was pressed in the `--preview` window during the camera warm-up. Check the USB connection, and do not press q or Esc in the preview window while the capture runs.
- **`Missing required calibration files`.** Stage 01 needs `intrinsic_results/<WxH>/oak_<MXID>.npz` for the capture resolution and `extrinsic_results/oak_<MXID>.npz` for every camera ([calibration.md](calibration.md#what-you-produce)).

### Stage 02: segmentation and fusion

- **`GroundingDINO found no box for prompt ...`.** The stage fails if any of the three cameras has no detection. Pass a better noun phrase, for example `--sam-prompt "green toy."`. The detection thresholds are not exposed by the pipeline. To diagnose, run the segmenter by hand with a lower threshold and look at the `.detections.jpg` and `.selection.json` written next to the output:

  ```bash
  python aura/perception/aura_segment_static_target_image.py \
    --img_path "$AURA_DATA_ROOT/franka_lift/<case>/anygrasp/color/0/0.png" \
    --output_path "$AURA_DATA_ROOT/debug/cam0_frame0_sam_rgba.png" \
    --TEXT_PROMPT "<object prompt>." --box-threshold 0.25
  ```

  This only diagnoses: the pipeline cannot use the RGBA image that a hand run of the segmenter writes ([Perception](#perception)). To use a lower threshold in the pipeline, lower the `--box-threshold` default (0.35) in `aura/perception/aura_segment_static_target_image.py` (stage 02 does not pass this option) and redo stage 02 ([Re-runs](#re-runs)). Restore 0.35 afterwards: the default applies to every case, and the paper's cases used 0.35. Each camera's `.selection.json` records the `box_threshold` used.
- **`missing model file: ...`.** Put the three Grounded-SAM-2 files into `$AURA_GSAM_CHECKPOINTS` ([Model weights](../environments/README.md#model-weights)).
- **An `ImportError` that names the Grounded-SAM-2 clone.** The missing module is `grounding_dino`, `groundingdino` or `sam2`: point `AURA_GSAM_REPO` at the clone from which `groundingdino` and `sam2` were installed, and install them from it (post-install step 3 of `environments/aura.yml`).
- **`No module named ...` for another module in the stage-02 log, for example `supervision`.** The `AuRA` env is incomplete: run the post-install steps and the sanity check in the header of `environments/aura.yml`.
- **Parts of the object are missing from the cloud.** SAM split the object into several components, and `--mask-object-id 0` keeps only the largest. Pass `--mask-object-id union`. The log line `components=K` and `num_components` in `mask_info_<N>.json` show the split. On an existing case, redo stage 02 as described under [Re-runs](#re-runs): `--resume` alone skips it while the `.npz` exists.
- **The cloud contains the table or the background.** Check in `anygrasp/mask/cam<N>_frame0_sam_rgba.detections.jpg` which box was chosen, and refine the prompt. Then redo stage 02 as in the previous entry.
- **Stage 02 fails with `zero-size array` and writes no `.npz`.** The fused cloud is empty: no masked pixel had depth between 0.2 and 1.5 m, or the filters removed everything. Check the masks and the camera distances.
- **The point count differs slightly between runs.** Open3D's radius outlier filter is not deterministic with several threads. For bitwise-identical results, run the preparation with `OMP_NUM_THREADS=1` exported.

### Stage 03: AnyGrasp

- **License, SDK or checkpoint errors** are covered in [anygrasp_license.md](anygrasp_license.md#troubleshooting).
- **The stage ends with a segmentation fault (exit 139) after the grasp files were written.** `--save_debug_images` needs a display, and without one Open3D crashes while rendering. Run the preparation from a desktop session. `--resume` then continues with stage 04, without the debug images.
- **`AnyGrasp produced no grasps, including fallback`.** If `logs/03_anygrasp_pose_generation.log` contains `license failed to pass`, the license check failed and AnyGrasp computed nothing: fix the license ([anygrasp_license.md](anygrasp_license.md#troubleshooting)), then run again with `--resume`. Otherwise, look at the fused cloud (`anygrasp/observation/visualization/`, `raw_to_fused_observation_run_meta.json`). Also check that the object fits the gripper: `--max-gripper-width` is 0.08 m. If the retry ran, its log (`logs/03b_anygrasp_pose_generation_no_collision.log`) also says `No grasp detected after collision detection.`, although stage 03b runs without collision detection: the wrapper prints this text whenever it finds no grasp.
- **`No grasp detected after masking`, followed by `TypeError: object of type 'NoneType' has no len()`.** AnyGrasp's object mask left no grasp, and the wrapper crashes on this empty result instead of reporting it, so the preparation stops at once, without the retry of stage 03b. Check the fused cloud as for the previous message, then redo stage 02 or capture again ([Re-runs](#re-runs)).
- **The retry ran.** `logs/03b_anygrasp_pose_generation_no_collision.log` exists, and the grasps come from `anygrasp_results_no_collision/`. The filter output still goes to `anygrasp_results/`, so execution needs no change.

### Stage 04: feasibility filter

**`PyRoki filtering accepted no grasps`.** Read the report first:

```bash
python - "$AURA_DATA_ROOT/franka_lift/<case>/anygrasp_results/grasps_table_ik_report.json" <<'EOF'
import json, sys
r = json.load(open(sys.argv[1]))
print(json.dumps(r["summary"], indent=2))
for e in r["entries"]:
    if not e["accepted"]:
        print(e["rank"], e["rejection_stage"], e["reason"])
EOF
```

| Most frequent `rejection_stage` | What to check or change |
|---|---|
| `home_to_hover_cartesian_robustness` | The reason names the failed test. `joint branch jump` is governed by `--max-waypoint-joint-delta-rad` (0.25). Endpoint joint change, total joint motion and Cartesian rotation are governed by `--max-home-hover-joint-delta-rad` (2.0), `--max-home-hover-total-joint-motion-rad` (8.0) and `--max-home-hover-rotation-deg` (120). The joint-limit margin is `--robust-joint-margin-rad` (0.16). Often it is easier to turn or move the object so that grasps need less wrist rotation. |
| `target_fingertip_table` | A fingertip would come closer to the table than `--clearance-m` (0.003 m), typically for flat objects. Check the [fingertip calibration](calibration.md#4-fingertip-geometry). |
| `target_camera_keepout` | The gripper would come within `--camera-keepout-radius-m` (0.12 m) of a camera. Move the object or the camera. |
| `coarse_world_z` | The grasp centre lies at or below the table plane, that is, at world z ≥ `--table-z` (0 m), since +z points down. Check the world frame (board flat on the table) and `--final-z-offset`. |
| `ik_fk_hover` | The hover pose is out of reach or close to a joint limit (`ik_fk_endpoints.hover`). Move the object towards the middle of the workspace. |
| `cartesian_hover_to_final_robustness`, `cartesian_final_to_lift_robustness` | The reason names the failed sample and check: `IK/FK or joint-margin check` (out of reach or close to a joint limit, as for `ik_fk_hover`), `IK branch jump` (a joint step above `--max-waypoint-joint-delta-rad`, 0.25), `fingertip/table clearance` or `camera keep-out` (as in the rows above; the lift pose is checked only here). |
| `exception` | Run the filter by hand with `--include-tracebacks`. |

- **Re-running the filter.** Re-run only the filter with new thresholds: `bash scripts/anygrasp_poses_one_shot.sh --resume --refilter --max-waypoint-joint-delta-rad 0.40 <case>`. The lift one-shot re-runs the filter by default, with the preparation defaults plus the options after `--`, not the options of an earlier preparation run: repeat the thresholds after `--`, or, with the default `--home`, pass `--no-refilter` to keep the safe list you inspected. Every relaxed threshold reduces a safety margin, and the renders cannot show it, because stage 03 draws them before the filter runs. Before you execute, check the values in the `table_ik_fk_check` block of the safe-list entry you will execute ([data_format.md](data_format.md#feasibility-filter-output)), then do the dry run and the hover-only test ([usage.md](usage.md#dry-run-and-hover-only-test)).
- **Running the filter by hand.** Run by hand, `aura/grasping/filter_grasps_table_collision_pyroki.py` uses its own defaults, not the values the preparation script passes:
  - Without `--out` and `--report` it writes next to the `--grasps` file, so on a case's `anygrasp_results/grasps.json` it overwrites the case's safe list and report. Pass both, with paths under `$AURA_DATA_ROOT/debug/<case>/`.
  - The camera keep-out check is off unless you pass `--camera-extrinsic-dir "$AURA_CALIB_ROOT/extrinsic_results"`, so a hand run without it can accept grasps the pipeline rejects.
  - Four thresholds are stricter: `--robust-joint-margin-rad` 0.20 (pipeline 0.16), `--max-home-hover-joint-delta-rad` 1.40 (2.0), `--max-home-hover-total-joint-motion-rad` 5.0 (8.0) and `--max-home-hover-rotation-deg` 100 (120).
  - The `configuration` block of the report records every threshold, offset and input path used, but not the IK weights (`--pos-weight`, `--ori-weight`, `--rest-weight`), which the preparation script leaves at their defaults.
- **Every grasp is rejected with `Current/start state failed joint-margin, table, or camera keep-out validation`.** The start state, `assets/fr3_home_state.npz`, fails the checks with your calibration: a fingertip near the table, a camera within 0.12 m of the gripper at home, or a joint near a limit. Check the calibration and the camera placement. If your robot's home configuration differs, capture a new state file ([`assets/README.md`](../assets/README.md)).
- **`Could not find both robot_calib_result.npz and a fingertip calibration JSON under ...`.** Install the fingertip file next to the hand-eye result ([calibration.md](calibration.md#4-fingertip-geometry)).
- **`No recognized OAK camera-to-world transform in NPZ/JSON files under ...`.** `extrinsic_results/` has no usable `oak_<MXID>` file.

## Execution and lift recording

- **`Unknown global option: ... Put preparation-only options after --`.** Options of the preparation script go after `--`. Set the offsets (`--hover-z-offset`, `--final-z-offset`, `--lift-z-offset`, `--rot-offset-rpy`) as global options, before `--`: the lift one-shot passes them to both the filter and the executor. The filter sees new values only when it runs again (the default `--refilter`); offsets given after `--` reach only the filter.
- **`--no-home requires an explicit fresh --state-file ...`.** The filter plans from the state file, so without homing it needs the robot's current configuration. No script in this repository writes one: save the arm's current 7 joint angles in rad under key `q` of an `.npz` (format in [`assets/README.md`](../assets/README.md)) and pass it as an absolute path. On a prepared case the file takes effect only if the filter runs again: keep the default `--refilter`. With `--no-refilter` (or `REFILTER=0`) the preparation skips the filter, and the arm moves from its current pose along a path checked from the old state file.
- **`Intrinsic directory missing: ...`** or **`Extrinsic directory missing: ...`**. The lift one-shot needs `intrinsic_results/1280x720/` and `extrinsic_results/` in `$AURA_CALIB_ROOT`, by default `calibration/` ([calibration.md](calibration.md#what-you-produce)). With `--record-resolution low` it also needs 640 × 400 intrinsics in `intrinsic_results/640x400/` ([calibration.md](calibration.md#1-camera-intrinsics)).
- **`safe-index N is out of range; accepted grasps: M`.** Pick an index below the number of accepted grasps.
- **`Selected grasp has no passing dense Cartesian robustness report; run --refilter`**, or the executor's `Selected grasp lacks a passing dense Cartesian robustness report`. The safe list comes from an older filter run. Re-run the filter: run the lift one-shot again with `--refilter` (its default, which `--no-refilter` and `REFILTER=0` turn off), or run `bash scripts/anygrasp_poses_one_shot.sh --resume --refilter <case>`.
- **`Selected grasp lacks the PyRoki hover target transform`.** The executor was given `grasps.json`; give it `grasps_table_ik_safe.json`.
- **`Stored PyRoki hover validation was generated for a different target/configuration`.** The filter and the executor disagree on the hover pose by more than 1 mm or 0.5°: a different `--hover-z-offset`, a different rotation offset, or a new calibration (a different `--final-z-offset` or `--lift-z-offset` is not detected). When running the executor by hand, pass `--rot-offset-rpy 0 1.57079632679 0` (its own default is no offset) and the same z offsets as the filter. After a recalibration, re-run the filter.
- **`... already exists but differs from --calib ...`** (recording executor) or **`Refusing to overwrite different preserved file`** (lift one-shot). A calibration or start-state file differs from the copy kept with this case or recording. Do not use the lift one-shot's `--overwrite`: it deletes the whole case, recording included.
  - The lift one-shot names `camera_calibration/intrinsic/...` on a re-run of a recorded case: the run most likely used another `--record-resolution` than the recording ([Known limitations](#recording-and-cameras)). Run again with `--no-refilter` and the recording's resolution (`record_resolution` in `phystwin/raw_recording/recording_summary.json`), which also restores `metadata.json`.
  - After a real recalibration: the lift one-shot compares only at its end, so it has already re-run the filter (default `--refilter`) and rebuilt `phystwin/calibrate.pkl` and `metadata.json` from the new calibration. Rebuild these two files from the case's own copies with the example in the docstring of `aura/conversion/calibration_matrix_to_phystwin_style.py`, but with `--intrinsic-dir "$CASE_DIR/camera_calibration/intrinsic" --extrinsic-dir "$CASE_DIR/camera_calibration/extrinsic"`, and record new data under a new case name.
  - A hand run of the recording executor: pass a new `--record-output-root`, or delete the old folder with its recording and calibration copy. `--overwrite-recording` (also when typed as `--overwrite`) does not lift this check.
- **`Fingertip calibration not found under ...`** or **`Cannot preserve missing file: .../oak_<MXID>.npz`** at the end of a lift run. These checks run only after the robot step and the conversion, so the recording in `<case>/phystwin/raw_recording/` is complete. Install the missing file, then run the same command again with `--no-refilter`, but without `--overwrite` (it deletes the recording), `--force-preparation` (it captures again) or `--finalize-existing-recording` (release and home already ran): the robot step is skipped, and no robot IP is needed.
  - The lift one-shot needs the fingertip file under the name `franka_fingertip_table_calibration_simple.json`, in `fingertip_calibration_results/` or directly next to `robot_calib_result.npz`, although the filter also accepts another `*fingertip*calibration*.json` (`configuration.fingertip_calib_path` in the report names the file it used).
  - The lift one-shot also needs `oak_<MXID>.npz` for every camera in `extrinsic_results/` and in the intrinsics folder of the recording resolution.
- **`Output folder ... already contains recording files`.** The recording folder already holds a recording (`bundle_*` folders, `recording_summary.json` or `session_summary.json`). The recording executor checks this only when the lift starts, after homing, hover, descent and grasp, so a dry run does not catch it; a hand run then continues the lift unrecorded and stops partway or completes, with the object still in the gripper. Before a hand run with `--execute`, pass a new `--record-output-root` or delete the old recording; `--overwrite-recording` skips the check but does not delete the old bundles. The lift one-shot checks the folder before any robot stage.
- **`Raw recording is incomplete (bundles=... summary=...)`.** An interrupted run left a partial recording. Delete `<case>/phystwin/raw_recording/` and run again. If it says `bundles=0` although the folder holds `bundle_*` folders, or a run ended with `Execution finished without raw recording bundles` right after recording, do not delete anything: the repository or data path contains `[`, `]` or `\`, which the check reads as pattern characters. Move the data to a path without them ([Known limitations](#known-limitations)).
- **`[resume] Complete raw lift recording already exists; robot execution will be skipped.`** This is expected for a finished case. The message comes after stage 01, which by default has already re-run the filter and rewritten `grasps_table_ik_safe.json`; to reuse a recording unchanged, run with `--no-refilter` and the recorded run's options, which are under `args` in `phystwin/raw_recording/recording_summary.json`: `--safe-index` (`rank`), the speeds, `--record-resolution` and `--record-fps`. `--finalize-existing-recording` still releases the object and homes the arm, and `--overwrite` deletes the case and starts over. If the run that wrote the recording ended with `[robot] ERROR`, it is the aborted take: start over with `--overwrite` or a new case name.
- **The run hangs after the hover move (`--hover-only`), or after `[abort] gripper reports no object; skipping lift`.** This is a known limitation of the recording executor ([below](#grasp-filtering-and-execution)). Press Ctrl-C. The arm stays where it stopped: at the hover pose, or at the grasp pose with the gripper open. Use the standalone executor for hover tests.
- **`Cannot read checkpoint input from /dev/tty`.** The recording executor's checkpoints read from the terminal. Run interactively, or pass `--yes`.
- **The lift run ends at the final `ROBOT CHECKPOINT` without waiting for Enter.** This last checkpoint, before release and home, reads standard input instead of the terminal: with standard input from `/dev/null` or an empty file the run stops there without a message (under `nohup` with a read error), and a line already waiting on standard input is taken as the answer. Without `--yes`, keep standard input on the terminal. If the run stopped there, the arm still holds the object at lift height: release it and move the arm clear yourself (next entry).
- **The robot stopped halfway.** After an abort or an error, the lift one-shot exits without its release-and-home step, so the arm stays where it stopped and may still hold the object. Release the object and move the arm clear yourself, for example from Franka Desk, before the next run.
- **`[robot] ERROR: ...` in the console.** The robot step failed, and the lift one-shot stopped before its release-and-home step, so the arm stays where it stopped: release a held object and move the arm clear yourself (previous entry). If the error came during the lift, the run still wrote a normal-looking recording to `<case>/phystwin/raw_recording/` (`offline_sync.num_saved_timesteps` in its `recording_summary.json`), and a plain re-run reuses it: it prints `[resume] Complete raw lift recording already exists`, skips the robot and converts the aborted take. The object has moved since the snapshot, so put it back and record the case again from a new capture: `--overwrite` (deletes the whole case) or a new case name.
- **`measured TCP did not move >0.0015m within 3.0s`.** The lift did not start, for example because of a reflex. Check the robot's state in Desk.
- **`joint soft-limit margin check failed`.** A joint came within `--cartesian-runtime-joint-margin-rad` (0.15 rad) of a soft limit, and the move was stopped. Execute another accepted grasp (`--safe-index`) or move the object.
- **`recorder cameras were not ready within 90s`.** A camera did not finish starting. The camera with an `Opening specific OAK by MXID: <MXID>` line but no `Opened oak_<MXID>` line hung: check its USB connection ([hardware.md](hardware.md#cameras)), or unplug and replug it.
- **The standalone executor rejects the grasp with `target outside workspace; use --allow-outside-workspace only if you are sure`** or `Cartesian workspace guard rejected this grasp: ...`. Its workspace box is in the robot base frame and defaults to x 0.20 to 0.80 m, y -0.40 to 0.40 m and z 0.00 to 0.60 m (`--workspace-*`). If your table lies below the plane the robot base is mounted on, grasp poses have a negative base z; on the authors' rig it is about -0.02 m. After checking the target, pass `--allow-outside-workspace` or lower `--workspace-z-min` for the hover test.
- **The standalone executor stops with `Motion failed: Interpolation times must be within the range [0.0, 1.0]`** right at the end of a move. This is a known issue of `move_to_pose` in the vendored `fr3` library: the arm has reached the target, but the script stops. The last `[motion]` line names the move. After `HOVER`, run it again. After `DESCEND` or `LIFT`, first release a held object and move the arm clear yourself, for example from Franka Desk: a rerun opens the gripper without a prompt as soon as it has connected, after homing from where the arm stopped if you pass `--home`.
- **The standalone executor aborts when you press Enter.** It asks you to type `yes` at each step; the recording executor accepts Enter.

## Cameras and synchronization

- **`Requested OAK(s) not detected: [...]`.** A camera in `AURA_OAK_IDS` (or `--oak-ids`; `--record-oak-ids` in the recording executor) is not among the available cameras, which most tools list just before as `Available OAK devices:`. Check that all three cameras are connected (`lsusb -d 03e7: | wc -l` prints `3`), that `AURA_OAK_IDS` holds exactly their MXIDs ([hardware.md](hardware.md#cameras)), and that the Movidius udev rule is installed ([System requirements](../environments/README.md#system-requirements)). A camera that another program or a crashed process still holds is not available either: quit that program, or wait a moment or unplug and replug the camera.
- **Many dropped timesteps, or, in a lift or teleoperation recording, `match_span_ms_p50` above about 45 ms.** Usually one camera delivers fewer frames than the others (`raw_frame_counts` in `recording_summary.json`). Some loss is normal on the authors' rig: in 24 of their 26 lift recordings, one camera delivered only 36 to 42 frames while the other two delivered 53 or 54, so 20 to 33 % of the timesteps were dropped, although all three cameras had reported `UsbSpeed.SUPER` (USB 3) in the static capture of the same case; `match_span_ms_p50` was 53 to 77 ms in 23 of the 26. Their human-baseline recordings dropped 8 to 25 %, with every camera on `UsbSpeed.SUPER`. With far more drops, or a camera whose `USB speed=` line at start-up reads `UsbSpeed.HIGH` (USB 2), fix the connection: use separate ports and good cables. Raising the sync tolerance only hides the problem. In recordings of `aura/capture/record_3oak.py` (static capture, calibration captures, human baseline), the matched times include each camera's receive latency, so `match_span_ms` there is not a reliable sign of this problem ([Known limitations](#recording-and-cameras)).
- **The recording stopped early, or a run aborted, after you pressed q, Esc or Ctrl-C.** Only q and Esc act in a preview window; closing the window stops nothing.
  - `aura/capture/record_3oak.py`: q or Esc stops the recording early and saves it; during the warm-up it leaves no frames (`No recorded frames for oak_<MXID>`). Run directly, it treats Ctrl-C the same way until the recording stops. A Ctrl-C after that loses the recording: during `Running offline fixed-rate synchronization...` nothing is written, and during `Saving N synchronized bundles ...` the bundles saved so far stay without `recording_summary.json`, so a rerun into that folder stops with `already contains recording files`; delete the folder or use a new one.
  - Teleoperation recorder: q or Esc ends the session, before anything is recorded if pressed during the warm-up.
- **q or Esc in the recording executor's preview did not stop the arm.** q or Esc is not an emergency stop; to stop the arm at once, use the emergency stop. In the preview (`--record-preview`), q or Esc stops a hover, descent or lift move at once, but not homing or a gripper action. Pressed before the hover move, for example during the camera warm-up, it does not stop the robot process at once: with `--yes` the arm still homes (`--home`, the lift one-shot's default) and opens the gripper, and the run stops at the start of the hover move, unless the robot process is killed first, about 10 s later, possibly mid-motion. Without `--yes`, answer the remaining checkpoints with `n`: a prompt left open can hang the executor until Ctrl-C.
- **Text labels appear in saved images.** With a preview scale of 1.0 (`--preview-scale`, or `--record-preview-scale` in the recording executor), the preview draws its camera labels into the recorded frames. Keep the default scale.
- **The calibration no longer fits after you changed `--enable-undistortion`.** The intrinsics are only valid for the setting they were fitted with, which is the default `True`.

## Teleoperation recorder

- **The arm moved right after launch.** `--home-on-start` defaults to `True` ([below](#recording-and-cameras)). Pass `--home-on-start False` to skip homing.
- **The arm drifts down or turns as soon as teleoperation starts.** A trigger rests at 0.0 instead of -1.0 ([hardware.md](hardware.md#gamepad)).
- **`No controller found. Connect a PS controller and try again.`** Connect the controller before you launch; without it the session ends at once, although homing on launch still happens.
- **`Output folder ... already contains recording files` after pressing Square.** The output check runs only when recording starts, after the arm has homed. Choose a new `--output-root` before launch.
- **`Square ignored: OAK recorder is not ready yet.`** Wait until the camera warm-up has finished.
- **The gripper keeps opening and closing.** Every D-pad press is queued and executed in turn. Press once and wait.
- **The recording is gone after Ctrl-C.** Stop with Square or Circle; Ctrl-C discards the frames held in RAM.
- **`Record toggle -> ON. Memory recording started.` after the recording has stopped.** Each launch records one session, so this press records nothing, but it restarts the robot-state capture: if it comes before the recorder has copied the robot states, the saved joint states are samples taken after the press, the bundles get large robot sync errors, and the hand-eye tool drops them. Once the recording has stopped (by Square, by `--max-duration`, or by q or Esc in the preview), do not press Square until the recorder prints `Done saving.`; Circle is safe.

## Human-baseline recorder

- **`Intrinsic calibration directory not found: ...`** or **`Extrinsic calibration directory not found: ...`**. The script needs `intrinsic_results/1280x720/` and `extrinsic_results/` in `$AURA_CALIB_ROOT`, by default `calibration/` ([calibration.md](calibration.md#what-you-produce)). With `--resolution low` it needs `intrinsic_results/640x400/` instead ([calibration.md](calibration.md#1-camera-intrinsics)).
- **`Case already exists: ... Choose another name or pass --overwrite.`** `--overwrite` deletes the whole case first.
- **The script needs an interactive terminal.** Enter stops the recording, and the frame range is asked for interactively. Without a terminal the recording runs for the full duration, and `--start-frame` and `--end-frame` skip the questions only if both are saved bundle indices and the end is not before the start. The valid range (`valid indices: 0..<last>`) is known only after the recording, because dropped timesteps shorten it, so choose values well inside the expected length. An invalid value falls back to the question; without a terminal the run then stops before the conversion (or waits while its input stays open). The raw bundles stay in `<case>/raw_recording/`, but the script cannot resume, and `--overwrite` deletes them.
- **`Recorder failed with exit code 130` after you pressed Enter, or `[interrupt] Stopping recorder safely...` after Ctrl-C.** The take is lost: record it again under a new case name or with `--overwrite`. Ctrl-C always loses the take. The script passes Enter to the recorder as Ctrl-C for as long as the recorder runs, so an Enter during the synchronization and save that follow a stop by the time limit (`--max-duration`, at most 30 s) or by q or Esc in the preview aborts the save. Press Enter once, before the time limit; after a stop by the limit or by q or Esc, type nothing until the frame prompt appears.
- **The recording failed right after `[READY]`, or the frame prompts answered themselves.** Keys typed in the terminal are queued. An Enter typed before `[READY] Recording is active` stops the recording as soon as it starts, so the recorder fails (`Recorder failed with exit code 1`) or saves too few bundles. Keys typed after the Enter that stopped the recording answer the frame prompts: an empty line takes the default (start 0, end = the last frame). The range used is printed as `[selection] keeping inclusive frames ...`.
- **Which numbers to enter.** The start and end frames are the frame numbers shown in `raw_preview_3oak_numbered.mp4`. Both ends are inclusive. Type them without leading zeros (`10`, not `010` or the `000010` of a bundle folder name): the script reads such a number as octal (`010` is 8), the converter as decimal. A zero-padded start stops the run after the conversion with `Converted frame count ... does not match selected count ...`; a zero-padded end silently converts a shorter range, while `hand_collection_summary.json` records the end you typed. After such a stop `raw_recording/` is still there; a rerun with `--overwrite` deletes it.
- **`Only N synchronized bundle(s) were saved; record a longer sequence`**, **`Timed out waiting for OAK recording to start`**, **`Recorder exited before recording started`.** See `<case>/recording_console.log` for the recorder's own error.

## Calibration

- **`Accepted only N valid views, need at least 10`.** Pass `--sample-every 1` and record a sweep that covers the whole image.
- **`KeyError: 'image_size'`.** Pass the intrinsic `.npz`, not the `.json` report.
- **`Image size mismatch`.** The intrinsics are for a different resolution than the capture.
- **`Not enough detections: markers=..., charuco=...`.** The board is partly hidden, too far away, or shows glare; or the flags do not match the printed board.
- **The overlay axes are not at the board corner, or the poses look wrong.** Check the print scale (40.0 mm squares) and the board flags.
- **`--camera-name is missing or empty`.** Set `AURA_HANDEYE_OAK_ID=oak_<MXID>` or pass `--camera-name`.
- **All or nearly all bundles are dropped as `drop_exception`.** This status covers any error raised while a bundle is read; the `error` of the printed examples, and of each record in `scan_records_debug.json`, names it:
  - `Camera '...' missing in meta sources`: `--camera-name` (default `$AURA_HANDEYE_OAK_ID`) is not a camera folder of the bundles; it must be the recorded hand-eye camera's `oak_<MXID>`, with the prefix;
  - `Image size mismatch`: the session was not recorded at the resolution of `--intrinsic-file`; the teleoperation recorder defaults to `low` (640 × 400), so record with `--resolution high`, and do not use `--ignore-image-size-check` for this;
  - `Not enough detections`: see above.
- **`Could not load intrinsics from session summaries`.** Pass `--intrinsic-file`.
- **`Only N samples remain after filtering; need at least 4`.** The run prints the counts per status and writes them to `--output-dir`: the bundle checks in `scan_records_debug.json` and the pose-diversity filter in `pose_filter_logs_debug.json`:
  - `drop_match_span` (only when several cameras were recorded): their capture times differ by more than `--max-match-span-ms` (45 ms); record only the hand-eye camera ([calibration.md](calibration.md#record-a-teleoperation-session)), or check for a camera on USB 2;
  - `drop_robot_delay`: the robot state is badly synchronized;
  - `drop_reproj_rms`: blurred or barely visible boards;
  - many `drop_too_similar` in `pose_filter_logs_debug.json` (counted as `keep_pre_pose_filter` in `scan_records_debug.json`): move through more distinct poses.
- **Large hand-eye residuals.** The board slipped in the gripper, the extrinsic of the hand-eye camera is wrong, or the motion was too fast (motion blur). If `Final inliers` equals `Pass pose diversity` while `outlier_logs` in `robot_calib_result.json` lists `drop_final_*` entries, the outlier step was skipped (fewer than 4 samples would have remained) and the residuals include those samples.
- **`Output must be empty: ...`** (re-anchoring). Give `--output-dir` a new folder on every run.
- **`... reprojection RMS ... exceeds ...` or `need >=8 ChArUco corners and >=4 markers`** (re-anchoring). Place the board where all three cameras see it fully and not too obliquely.
- **`Only N contact observations found`** or **`Cannot infer left/right from contact name`** (fingertip fit). At least 6 contacts are needed, and contact names must contain `right` or `left`.

## Known limitations

v1 documents these behaviours of the reference pipeline and does not change them.

### Grasp filtering and execution

- **The feasibility filter is not a full collision checker.** It checks:
  - the two calibrated fingertip points against the table plane, at the grasp and along the sampled paths;
  - five tool points (the TCP, both fingertips, and the points halfway between the TCP and each fingertip) against 0.12 m keep-out spheres around the camera centres;
  - IK, forward kinematics, joint-limit margins and joint continuity along a densely sampled Cartesian path from home to hover, and along the descent and the lift.

  The arm links, the hand body, self-collision, the object itself and the camera mounts are not modelled; the report states this in `configuration.path_check_scope`. Inspect the renders before you execute.
- **`--hover-only` hangs the recording executor** (`aura/robot/execute_anygrasp_franka_record_lift.py`), and therefore `scripts/run_anygrasp_to_lift_one_shot.sh --hover-only`. After the hover move, the robot process ends without notifying the recorder, which keeps waiting for a lift. The `gripper reports no object; skipping lift` abort ends the same way. Exit with Ctrl-C. For hover tests, use the standalone `aura/robot/execute_anygrasp_franka.py --execute --home --hover-only` with the arguments of [usage.md](usage.md#dry-run-and-hover-only-test), including `--rot-offset-rpy 0 1.57079632679 0`.
- **The planning start state is a file, not the live robot.** The filter plans from `assets/fr3_home_state.npz`. This is valid only because the lift one-shot passes `--home` to the recording executor by default, so the arm starts from the pose at which the file was measured. The one-shot's `--no-home` therefore requires an explicit, freshly captured `--state-file`, and no script in this repository writes one ([`assets/README.md`](../assets/README.md)). On a prepared case it also needs the default `--refilter`, which the script does not check ([above](#execution-and-lift-recording)). The executors themselves home only when you pass `--home`, which is off by default. When you run one by hand with `--execute`, pass `--home` unless the filter's `--state-file` was captured at the arm's current pose ([hardware.md](hardware.md#robot)).
- **Keep `[`, `]` and `\` out of the repository and data paths.** The lift one-shot looks for recorded bundles with `compgen -G "$RAW_RECORDING_DIR/bundle_*"` (three times in `scripts/run_anygrasp_to_lift_one_shot.sh`), which reads the whole path as a pattern: a `[`...`]` pair becomes a bracket expression and a `\` escapes the next character, so the real folder no longer matches itself. A complete recording is then reported as `Raw recording is incomplete (bundles=0 summary=1)`, or a new case stops with `Execution finished without raw recording bundles` after the lift, and the recording is never converted. `*` and `?` in the path still match themselves but can also match sibling folders, so avoid them too. Move the data, or the checkout, to a path without these characters.
- **Only the first failed check of each grasp is recorded.** The report's `rejection_counts` therefore understate how many grasps would fail each individual check. For rejected grasps, the statistics computed from the waypoints stop at the failing waypoint, and the home-to-hover joint-motion values (`total_joint_motion_l1_rad`, `max_waypoint_joint_delta_rad`, `endpoint_max_joint_delta_rad`) stop one waypoint before it, without the failed step: use `reason` and `waypoints` for such grasps.
- **Two sets of parameter values.** The preparation script loosens four filter thresholds relative to the filter's own defaults ([Running the filter by hand](#stage-04-feasibility-filter)), and passes observation-filter values that differ from the defaults of the fusion script ([data_format.md](data_format.md#segmentation-and-observation-cloud)). Running either tool by hand without the script's arguments gives different results.
- **Safe index 0 is the accepted grasp with the least joint motion** from home to hover (ties go to the higher AnyGrasp score), not necessarily AnyGrasp's best grasp. `best_grasp.json` and `debug_best_grasp.png` show AnyGrasp's rank 0, which is executed only when it passes the filter and also needs the least motion. The `rank` field of each safe-list entry is its AnyGrasp rank, and the lift one-shot prints it as `Original AnyGrasp rank`; `--safe-index N` executes another accepted grasp.
- **The paper's cases used stricter filter thresholds**: `--clearance-m 0.005 --robust-joint-margin-rad 0.2` instead of the preparation defaults 0.003 m and 0.16 rad. Pass both to `scripts/anygrasp_poses_one_shot.sh`, or re-filter an existing case with `--resume --refilter` and these values. The lift one-shot re-runs the filter of a prepared case with the preparation defaults, so pass them to it as well, after `--` ([usage.md](usage.md#step-1-preparation-no-robot-motion)).
- **The lift one-shot first re-runs the filter of every existing case**, a case you have just prepared included (default `--refilter`). It uses the preparation defaults plus the options of this call, not those of an earlier preparation run, and rewrites the safe list before it checks for a recording. It can therefore execute a grasp you did not inspect, stop the re-run of a recorded case before the release and the conversion, or leave the `safe_index` in `global_one_shot_summary.json` pointing into a new list. Repeat your filter options after `--`, or, with the default `--home`, pass `--no-refilter` and the options of the earlier run.
- **Grasp success is effectively not checked.** With the defaults `--grasp-width 0.0` and `--grasp-epsilon 0.08`, the gripper reports a grasp even when it closes on nothing, so the lift goes ahead. The lift one-shot does not expose these options. Watch the checkpoints.
- **The recording executor ignores the workspace box and the Joint-4 guard.** It accepts `--disable-workspace-check`, `--allow-outside-workspace`, `--workspace-*`, `--joint4-*` and `--disable-joint4-check` for compatibility, but they have no effect; its printout may still say `target workspace check: BAD`. Its runtime safeguards are the filter upstream, a joint-limit margin checked in every control cycle (`--cartesian-runtime-joint-margin-rad`, 0.15 rad) and the robot's collision reflexes.
- **Only the hover pose is checked against the safe list.** The recording executor takes the descent and lift heights from its own `--final-z-offset` and `--lift-z-offset` without checking them against the filter's: with other values, the descent or the lift goes to a pose the filter never checked. Use the filter's offsets; with the lift one-shot, give them before `--`.
- **The standalone executor differs from the recording executor.**
  - It does not read the checks the filter stored in the safe list (no robustness check, no hover cross-check) and also accepts `grasps.json`. Its own `--rot-offset-rpy` default is no offset: without `--rot-offset-rpy 0 1.57079632679 0` its dry run still passes, but the hover pose is turned by 90°.
  - It moves with the `fr3` wrapper, so its `--motion-speed` and `--descend-speed` are speed fractions (0 to 1), not m/s.
  - It enforces a workspace box whose default z range starts at the base plane.
  - Its `move_to_pose` can stop with an interpolation error at the very end of a move (see [above](#execution-and-lift-recording)).
- **Speeds.** The recording executor's `--motion-speed`, `--descend-speed` and `--lift-speed` are average linear speeds in m/s. The minimum-jerk profile peaks at 1.875 times that value. Every move takes at least 0.35 s and at least its rotation angle divided by `--servo-max-angular` (0.4 rad/s), so the move to hover, the only one that rotates the gripper, is slower when the rotation is large. The recording executor's own `--descend-speed` default is 0.05 m/s, not the lift one-shot's 0.02 m/s (their `--motion-speed` and `--lift-speed` defaults, 0.10 and 0.05 m/s, are the same), so pass `--descend-speed 0.02` when you run it by hand with `--execute`.
- **The object is released where the lift ended** (`--release-after`, the default), about 15 cm above its starting height, not lowered first.
- **Run the recording executor by hand only with `--record-output-root`.** Its default output folder assumes cases directly under a folder named `data`, which does not match the `franka_lift/` layout.
- **The recording executor copies the calibration first.** It refuses to start if a different `robot_calib_result.npz` is already in the output folder. Because the copy is made before the grasp is validated, a rejected run can leave that file in an otherwise empty folder.
- **Do not disable the soft joint limits for grasps you execute** (`--no-soft-limits` of the preparation script, `--disable-soft-limits` of the filter). The filter then stores no soft-limit margin, and the recording executor fails on the missing value.
- **Flags without effect**, kept for compatibility:
  - in the recording executor: `--servo-*` other than `--servo-max-angular`, and `--record-warmup-before-lift`;
  - in the fusion script: `--frames-for-pcd` (`--z-positive-down` restates the default and only undoes an earlier `--z-positive-up` on the same command line);
  - in the AnyGrasp wrapper: `--apply_object_mask` and `--debug_flip_z` (both restate the default and only undo an earlier `--no_` form on the same command line).

### Recording and cameras

- **The pipeline needs exactly three cameras.** The scripts check only that `AURA_OAK_IDS` is not empty. With fewer MXIDs, a new case stops in stage 02 (`Invalid camera index 2; valid range is 0..1` with two), after capture and segmentation but before any robot motion, and the human-baseline recorder stops in stage 05 (`No PNG frames for camera 2`) after recording and conversion. With more, stage 02 still segments every camera, so each needs a detection, but only cameras 0 to 2 go into the observation cloud and the MP4 previews. Do not change `AURA_OAK_IDS` between the preparation and the lift of a case: a lift that resumes a three-camera case with fewer MXIDs moves the robot and records before it stops in stage 03b.
- **Synchronization is software-only.** Frames are matched to a 15 Hz grid within 45 ms (lift, teleoperation and human-baseline recordings), 70 ms (static snapshot) or 75 ms (as used for calibration captures). A camera on USB 2 makes the recorders drop timesteps.
- **The camera-only recorder matches frames on capture time plus receive latency.** `aura/capture/record_3oak.py`, and so the human-baseline recorder, adds each camera's receive latency, frozen at the end of the warm-up (`projectors.<camera>.fixed_offset` in `meta.json`), to that camera's capture timestamps. The latencies differ between cameras, so one bundle can hold frames captured one to three frame periods apart, and `match_span_ms` does not show it; `sources.<camera>.device_ts` holds the capture times. The robot recorders match on the capture time; static captures are not affected, because nothing moves.
- **Recordings are held in RAM.** Limits: 30 s for `aura/capture/record_3oak.py` and the human-baseline recorder; 30 s by default and 60 s at most for the teleoperation recorder; 60 s by default and 120 s at most for the lift (`--record-max-duration`).
- **Bundle numbers are not timestamps.** Bundles are numbered without gaps even where timesteps were dropped, and the first few bundles often carry an extrapolated robot state (`interpolation_extrapolated`), with the largest error in bundle 0. The camera-only recorder's `target_ts_estimate` is wrong after the first dropped timestep ([data_format.md](data_format.md#bundle-metadata-metajson)).
- **Images are stored as JPEG** (quality 90, or 85 in the recording executor). The PNGs of the converted cases are lossless re-encodes of these JPEGs.
- **An aborted lift still writes a normal-looking recording.** Check the console and `offline_sync.num_saved_timesteps` ([above](#execution-and-lift-recording)).
- **A re-run of the lift one-shot converts with that run's `--record-resolution`**, not the recording's. A `low` recording re-run without `--record-resolution low` gets the 1280 × 720 `K` and `WH` in `metadata.json` and `"resolution": "high"` in `global_one_shot_summary.json`, without an error; a case that was already converted stops with `Refusing to overwrite different preserved file: .../camera_calibration/intrinsic/...` after `metadata.json` was rewritten. Run again with `--no-refilter` and the recording's resolution (`record_resolution` in `phystwin/raw_recording/recording_summary.json`), which also restores `metadata.json`.
- **What `--overwrite` deletes in the recording tools.**
  - Nothing: the `--overwrite` of `aura/capture/record_3oak.py` and of the teleoperation recorder, and the recording executor's `--overwrite-recording`. They only skip the check for existing recording files, so old bundles from an earlier, longer recording remain in the folder. Use new folders.
  - The whole case: the `--overwrite` of the lift one-shot and of the human-baseline recorder.
  - An existing `--output-root` and `--work-root` (default `<output-root>_work`), before recording: `aura/capture/anygrasp_data_collection.py --overwrite`. Without `--keep-work-root`, this script also deletes the work root, raw bundles included, after a successful run, with or without `--overwrite`.
- **q or Esc in a preview window ends the recording or the run, but it is not an emergency stop**, and closing the window stops nothing. In the recording executor it does not keep the robot from starting; what it does in each recorder, also during the camera warm-up, is described [above](#cameras-and-synchronization).
- **Cameras can stay busy after a crash**, because the DepthAI devices are released only when the process ends ([above](#cameras-and-synchronization)).
- **What each recorder stores about the robot.** Lift recordings store the robot state only in each bundle's `meta.json`, without `robot_states_raw.npz` or the control success rate. Teleoperation recordings store joint angles, but no end-effector pose.
- **The `calibration_manifest` of a lift recording can be empty or list extra cameras.** The recording executor fills it from every `oak_*.npz` in `$AURA_CALIB_ROOT/intrinsic_results/<WxH>/`, also for cameras it did not record, and writes `{}` if it finds none, for example when a hand run's `AURA_CALIB_ROOT` contains an unexpanded `~`; it prints `... loaded from matching calibration files when available` either way. The lift one-shot keeps the intrinsic files of the case's cameras in `phystwin/camera_calibration/intrinsic/`.
- **The teleoperation recorder** ([above](#teleoperation-recorder)):
  - moves the robot to home on launch (`--home-on-start True`), without a prompt;
  - records one session per launch;
  - defaults to the `low` resolution and to the current directory as output;
  - always grasps at width 0 with 20 N;
  - queues rapid D-pad presses;
  - checks the output folder only when recording starts;
  - loses the recording on Ctrl-C.

### Perception

- **Segmentation keeps exactly one GroundingDINO box per camera** (the most confident one after non-maximum suppression) and segments it with SAM 2.1. A camera without a detection fails stage 02, even a camera excluded with `--observation-cams`. The detection thresholds cannot be set from the pipeline, and the fusion script's `--skip-sam` reads only the binary component masks `anygrasp/mask/<N>/<component>/0.png` (non-zero pixels; every camera needs one), not the RGBA of a hand run of the segmenter.
- **`--mask-object-id 0` keeps only the largest mask component.** Parts of an object that appears split in the image are dropped silently; use `union`.
- **The prompt derived from the case name** drops only a trailing `_<digits>`.
- **Only depth between 0.2 and 1.5 m is used.** The preparation script does not expose this range.
- **An empty cloud stops stage 02** with an opaque `zero-size array` error.
- **Point counts can differ by a few points between runs**, because Open3D's radius filter is not deterministic with several threads.
- **Stage 03 needs a display** for its debug images; without one it can crash after writing the grasps.
- **The static capture requires the `.npz` calibration file** of every camera, although the converter prefers the `.json`.

### Calibration tools

- **Some defaults are traps** ([above](#calibration)). `--sample-every` defaults to 30. The hand-eye `--camera-name` comes from `AURA_HANDEYE_OAK_ID` and needs the `oak_` prefix, and `--diagnose-only` exits 0 even when every bundle was dropped. `--intrinsic-file` is effectively required, and the intrinsic `.json` cannot be used as `--intrinsic-file`. The default output locations are not where the pipeline reads.
- **The fingertip JSON is both the fitter's input and the fit result the pipeline reads.** The fitter never writes the `trajectories` block.
- **The two extrinsic tools treat distortion differently.** `Extract_extrinsic.py` uses the stored residual distortion; `calibrate_3oak_anchor108.py` assumes zero distortion unless you pass `--raw-distorted`. The two can therefore give slightly different extrinsics for the same image.
- **`calibrate_3oak_anchor108.py` has fixed inputs.** The 4 × 5 board and the 1280 × 720 intrinsics are built in.
- **The JSON reports record your input paths verbatim** ([data_format.md](data_format.md#before-sharing-data)).

### Human baseline

- **Interaction.** The recorder needs an interactive terminal and cannot resume. `--overwrite` deletes the whole case. `--end-frame` is inclusive here, but exclusive in `aura/conversion/raw_data_to_phystwin_style.py`. Until the recorder exits, the script passes Enter to it as Ctrl-C, so an Enter after the recording has stopped on its own aborts the save, and keys typed ahead answer the frame prompts ([above](#human-baseline-recorder)).
- **No robot state.** Human-baseline cases record no robot state, so controller trajectories for them cannot be derived from the robot's kinematics.

### Third-party components

- **The AnyGrasp license is machine-locked.** It is tied to the MAC addresses of the workstation's wired network interfaces and cannot be transferred. Adding or removing a wired adapter can invalidate it. The license tools also need OpenSSL 1.1, `ifconfig` and `iwconfig` ([anygrasp_license.md](anygrasp_license.md)).
- **The license of the vendored `fr3` library is still to be confirmed by its authors** ([`third_party/fr3/README.md`](../third_party/fr3/README.md)). Its `JointMotionGenerator` (`src/fr3/_motion.py`) is derived from libfranka and stays under the Apache License 2.0 ([`LICENSE-libfranka`](../third_party/fr3/LICENSE-libfranka)). Parts of `aura/robot/gamepad_record_franka_3oak.py` are adapted from `fr3` and fall under the `fr3` license ([THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)).

### Conversion (running the converters by hand)

The pipeline scripts pass the right arguments to the raw converter (`aura/conversion/raw_data_to_phystwin_style.py`) and the calibration converter (`aura/conversion/calibration_matrix_to_phystwin_style.py`). When you run them yourself:

- **`--make-mp4` fails in the `AuRA` env** with `Failed to open video writer: .../color/0.mp4`. It asks for the H.264 (`avc1`) codec, which the env's OpenCV cannot write; the frames are written by then, but `metadata.json` is not. Convert again without `--make-mp4`. With an OpenCV that can write `avc1`, also pass `--fps 15`: the default 30 plays the 15 fps recordings at double speed.
- **Pass the same `--camera-order` to both converters**: `oak_<MXID>` for each MXID in `AURA_OAK_IDS`, in that order. Without it, the raw converter numbers the camera folders alphabetically, and nothing checks that order against `calibrate.pkl`.
- **Re-convert into an existing folder only with `--overwrite`.** Without it, frames of an earlier, longer conversion stay in `color/`, `depth/` and `source_meta/`, although `metadata.json` lists only the new ones.
- **The calibration converter replaces `metadata.json`.** Copy the raw converter's file to `conversion_metadata.json` first ([data_format.md](data_format.md#conversion-record-conversion_metadatajson)).
- **Pass `--frame-num` to the calibration converter.** Without it, the count comes from the existing `metadata.json` or from `color/0/*.png`; if neither exists, `frame_num` is written as `null`, and the fusion script of stage 02 fails on it.
- **The calibration converter ignores a `--crop` for a camera that is not in `--camera-order`**, whereas the raw converter rejects it. Pass the same `--crop` arguments to both.
